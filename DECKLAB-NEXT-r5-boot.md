# r5-boot: Mixxx's loading screen is Deck Lab's boot picture

## What changed
- **No Mixxx logo while Mixxx loads.** `res/skins/DeckLab/skin.xml` gets a `<LaunchImageStyle>`. The
  LaunchImage shows the Deck Lab boot screen's last frame, at the same pixels: ink #0D0F12, the
  wordmark, and the waveform with the playhead parked on the cue under the wordmark's own playhead
  (`res/skins/DeckLab/boot/launch.png`, 800x480, centred). The appliance's Plymouth theme ends on
  this frame and its kiosk keeps it on the console and the X root, so the screen does not change when
  Mixxx's window appears.
- **The progress bar is the waveform.** The QProgressBar box sits on the waveform; its contents start
  at the cue. The chunk uncovers `boot/loading.png` (the bars after the cue in deck 1's cyan), so the
  waveform fills from the cue to its end as Mixxx loads (0 % = the boot frame exactly).
- `src/skin/legacy/launchimage.cpp/.h` (small):
  - a skin's own launch style is never replaced by the holiday logo (`isIn2024ChristmasHolidays()`
    now only swaps Mixxx's default logo; it used to override every skin from 24 Dec to 6 Jan);
  - `Q_PROPERTY(int spacing)`: `LaunchImage { qproperty-spacing: 0; }` removes the style's layout gap
    between the image and the bar, so the bar's position no longer depends on the Qt style or DPI.
    Skins that don't set it are unchanged.
- `tools/decklab/test_launch_image.py` (new, standard library): finds the parked playhead and the
  waveform in `boot/launch.png` and checks the QProgressBar margins and size in `skin.xml`, and that
  `boot/loading.png` covers the bar exactly, without assuming the art is centred. `test_build_pi.py` imports
  it, so the CI guard step and `python tools/decklab/test_build_pi.py` run it. Deck Lab's
  `build_assets.py --skin-dir` checks the numbers before writing and writes nothing on a mismatch.
- `tools/decklab/pi-build-lock.json`: `res/skins/DeckLab/skin.xml` hash refreshed.

The two images are generated by Deck Lab's `brand/build_assets.py --skin-dir res/skins/DeckLab/boot`
from the Plymouth layers, through the same arithmetic as the boot script. The QSS numbers
(margin `98px 0 0 385px`, contents 335x96) are printed by that script.

## Verified locally (WSL 2, Qt 6.4)
- `g++ -std=c++20 -fsyntax-only -Wall -Wextra -DQT_USE_QSTRINGBUILDER` on `launchimage.cpp` with the
  moc'd header: clean.
- Offscreen harness linking the real `launchimage.cpp`, the skin's `<LaunchImageStyle>` (with the
  parser's `skin:` path rewrite), the skin's `MinimumSize` and a QMainWindow set up like
  `initializeWindow()`, rendered at 800x480 with Fusion and Windows styles and at 1280x720:
  - 0 %: pixel-identical to the boot frame (and to the appliance's X root bridge);
  - 50 % / 100 %: differences only inside the waveform after the cue (x 427-591 / 427-760);
  - bar box at (40, 143) 720x194, contents at (425, 241); `spacing()` reads 0;
  - 1280x720: the frame centred on ink, same alignment.
- `python tools/decklab/build_pi.py --check-inputs` PASS; `test_build_pi.py` 10 tests OK;
  `python -m unittest tools/decklab/test_launch_image.py` OK; a launch.png shifted by 1 px fails it.

## Follow-ups
- App side of boot-to-play continuity (audit Signature 6): after the skin loads, a 400 ms transform
  from this frame into deck 1's lane (`DeckLabBootFrame` overlay that suppresses the waveforms while it
  animates). "Restarting" reuses the boot art; "Turning off" uses the appliance's shutdown frame (playhead at the
  start, "TURNING OFF", "UNPLUG WHEN THE GREEN LIGHT STOPS BLINKING"), never a finished-track or safe-to-unplug state.
- On screens of at least 1600x960 Plymouth and the appliance's X root use @2x art; the LaunchImage
  stays 1x there, so the picture halves when Mixxx's window appears (big HDMI screens on a Pi 4 or 5).
  Fix: `launch@2x.png`/`loading@2x.png` from build_assets and a LaunchImage switch by window size
  (margins doubled: `196px 0 0 770px`, contents 670x192).
